# Backend API docs: how they are built, and what to update when merging open PRs

Written 2026-10-19 on branch `dna-docs-improvements`. Keep this file until the
PRs listed below are merged and their follow-ups done, then fold anything
still useful into `backend/README.md` and delete it.

## 1. What the docs branch did

The goal was to make the backend API usable by someone outside the project
(a ShotGrid or AYON tooling developer building, say, a transcription recorder
inside ShotGrid). The gaps found, and where each was fixed:

| Gap | Fix | Lives in |
|---|---|---|
| No way to tell which endpoints proxy ShotGrid vs. store data in DNA | `x-tagGroups` ("Production Tracking" / "DNA"); tag descriptions rewritten; new tags `Publishing` and `Project Glossary` | `src/dna/openapi_schema.py` (`TAG_GROUPS`), `src/main.py` (`tags_metadata`) |
| IDs undescribed (and the docs site showed them as `integer` from a stale spec copy) | Every `*_id` / `user_email` / `platform` / `meeting_id` parameter gets a description injected centrally | `openapi_schema.PARAM_DESCRIPTIONS` |
| Zero request/response examples | `ConfigDict(json_schema_extra={"examples": [...]})` on 48 models, one fictional production throughout (project `124`, playlist `45`, version `6990` "mk020_0010_comp_v003", `sam.reviewer@studio.example`) | `src/dna/models/*.py`; dict-returning routes use `responses={200: {... "example": ...}}` in `main.py` |
| No error documentation | `ErrorResponse` model; 401 injected on every authenticated op; `responses=error_responses(404, ...)` on routes that raise | `src/dna/models/errors.py`, `openapi_schema.error_responses`, route decorators |
| No auth story, no concepts, no WebSocket docs | Hand-written pages | `dna-docs/api/{index,authentication,concepts,errors,realtime}.mdx` |
| Docs site spec copy drifted (3 weeks stale) | `npm run build:full` now runs `fetch-openapi` first | `dna-docs/package.json` |
| Too many code-sample languages | cURL, Python, JavaScript, C, Rust, Go | `dna-docs/docusaurus.config.ts` (`languageTabs`) |

Guards added to `tests/test_openapi_spec.py`: every tag in exactly one group,
every authenticated op has a 401, every parameter has a description, every
documented error body is `ErrorResponse`. **These will fail on a merge that
adds a tag, a parameter name, or an error response without updating the
places above - that is the point.**

### The pipeline

```
src/main.py + src/dna/models/*  --app.openapi()-->  docs/openapi.json   (make openapi, or .venv/bin/python scripts/export_openapi.py)
                                                          |
                           dna-docs: npm run fetch-openapi (copies + injects servers)
                                                          |
                           npm run regen-api-docs  -->  dna-docs/api/reference/*.mdx (gitignored)
                                                          |
                           npm run build           -->  site
```

`npm run build:full` does the last three. **Never hand-edit either
`openapi.json`; regenerate.** The drift test (`test_spec_file_is_up_to_date`)
fails CI otherwise.

## 2. Merge order and conflicts

Both `backend/docs/openapi.json` and `dna-docs/openapi/backend.json` are
regenerated by this branch *and* by #224 and #236. Expect conflicts there in
whatever order you merge. Resolution is always the same: take either side,
then regenerate both files from the merged code:

```bash
cd backend && .venv/bin/python scripts/export_openapi.py && .venv/bin/python -m pytest tests/test_openapi_spec.py
cd ../dna-docs && npm run build:full
```

`src/main.py` will also conflict where #224/#236 touched route decorators
that this branch added `responses=` / longer `description=` to. Keep both
sides' intent: the new field/enum from the PR, the `responses=` line from
this branch.

Suggested order: **this branch first**, then #224, #236, #233, #239. Each
PR's follow-up is then a small, mechanical edit listed below.

## 4. Known gaps left open on purpose

Decided during the docs work; documented as-is on the site rather than
changed in a docs PR:

- **`user_email` is trusted on most writes.** Only
  `/users/{user_email}/...` routes check it against the token
  (`emails_match` in `main.py`). Draft notes, `publish-notes`,
  `generate-note`, `run-qc-checks` accept any owner. The Authentication page
  has a warning callout. If this is ever tightened, update that page and
  `PARAM_DESCRIPTIONS["user_email"]`.
- **`/ws` has no authentication.** Documented on the Authentication and
  Real-time pages.
- **No service-to-service auth.** Tokens are Google OAuth for the
  deployment's `GOOGLE_CLIENT_ID` or anything under `AUTH_PROVIDER=none`.
  Community PRs #164 (ShotGrid PAT auth) and #96/#48 (ShotGrid login) were
  not reviewed here, but any of them landing means rewriting
  `dna-docs/api/authentication.mdx` and the "Authentication" section of
  `API_DESCRIPTION` in `main.py`, and adding their new `Auth` tag to
  `TAG_GROUPS` (the test will insist).
- **No pagination, no webhooks.** Stated on the Concepts page.

Deferred "nice to haves" from the same discussion, in rough value order:

1. `x-codeSamples` on the hero endpoints (`publish-notes`, draft PUT,
   `generate-note`) - hand-written snippets instead of generated ones.
2. An environment-variable reference page on the docs site (today split
   across `backend/README.md`, `SHOTGRID_SETUP.md`, and the Concepts page's
   "deployment flags" table).
3. Document `POST /find` operator semantics per provider (today: "same shape
   as `shotgun_api3` filters").
4. A versioning / stability statement. The spec says `0.1.0` and nothing
   about compatibility.
5. A "writing a production-tracking provider" page for people integrating
   DNA with AYON/ftrack/etc. (the `ProdtrackProviderBase` contract).

## 5. Verifying docs changes

The API explorer (examples, language tabs, Send-request panel) is rendered
client-side, so grepping `dna-docs/build/**/*.html` for example values finds
nothing. Check the generated page data instead - the `api:` front matter in
`dna-docs/api/reference/*.api.mdx` is zlib+base64:

```bash
cd dna-docs && node -e '
const fs=require("fs"),zlib=require("zlib");
const f=process.argv[1];const m=fs.readFileSync(f,"utf8").match(/^api: (.+)$/m);
const a=JSON.parse(zlib.inflateSync(Buffer.from(m[1],"base64")));
console.log(a.jsonRequestBodyExample, Object.keys(a.responses));' \
  api/reference/publish-notes-playlists-playlist-id-publish-notes-post.api.mdx
```

Or just `npm run serve` and look.
