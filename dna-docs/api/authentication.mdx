# Authentication

Every protected request carries a bearer token and an identity header:

```http
Authorization: Bearer TOKEN
X-User-Id: user@studio.example
```

`X-User-Id` must be the signed-in user's **email** and must match the
principal derived from the token. A missing or mismatched identity is
`403 Forbidden`.

Public, no token needed: `GET /`, `GET /health`, `GET /version-statuses`,
`GET /api/mock-thumbnails/{version_id}`, `GET /transcription/extension/health`,
`POST /auth/login`, `POST /auth/refresh`. Every other reference page shows a
lock icon. `GET /auth/me` is authenticated.

## What the token is

The DNA backend does **not** mint its own JWT and does **not** store sessions
or tokens in a database. The configured `AUTH_PROVIDER` validates the bearer
token and returns the caller's email (and, for ShotGrid, login).

| `AUTH_PROVIDER` | Login | Accepts on requests |
|---|---|---|
| `none` (default; development) | Email form on the frontend, or `POST /auth/login` | Any string; email is the string itself if it contains `@`, otherwise `STRING@localhost`. Identity header is optional; when present it must match. |
| `google` (production OAuth) | Google OAuth in the browser | A Google OAuth **ID token** (JWT) or **access token** issued to the deployment's `GOOGLE_CLIENT_ID`, for an account with a verified email |
| `shotgrid` | Username + legacy password via `POST /auth/login` | A ShotGrid REST **access token** obtained from `/api/v1.1/auth/access_token` |

The frontend stores the access token (and ShotGrid refresh token when present)
in a cookie and copies it into localStorage for compatibility. API calls still
send `Authorization: Bearer …` because the SPA and API often sit on different
origins.

### ShotGrid login

Each user must complete the one-time
[Flow Account Setup](/docs/2-account-setup) (bind an Autodesk PAT in Flow and
enable Legacy Login) before `POST /auth/login` will succeed. The password is
the **legacy passphrase**, not the PAT and not the Autodesk Account password.

```bash
curl -X POST "$DNA/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"username":"artist","password":"LEGACY_PASSWORD"}'
```

Response:

```json
{
  "token": "sg-access-token",
  "refresh_token": "sg-refresh-token",
  "expires_in": 600,
  "principal": {
    "email": "artist@studio.example",
    "login": "artist",
    "provider": "shotgrid",
    "name": "Artist"
  }
}
```

Access tokens are short-lived. Call `POST /auth/refresh` with the refresh
token (also not stored server-side) to get a new pair. The web app does this
once on `401` before signing the user out.

### Getting a token for your tool

- **Development (`AUTH_PROVIDER=none`):** send the user's email as the token
  and as `X-User-Id`.

  ```bash
  curl "$DNA/projects/user/sam.reviewer@studio.example" \
    -H "Authorization: Bearer sam.reviewer@studio.example" \
    -H "X-User-Id: sam.reviewer@studio.example"
  ```

- **Google:** obtain a Google OAuth token for the **same client ID** the
  deployment validates, then send it with matching `X-User-Id`.

- **ShotGrid:** use `/auth/login` (and `/auth/refresh`) as above. Pair
  `AUTH_PROVIDER=shotgrid` with `VITE_AUTH_PROVIDER=shotgrid` and set
  `SHOTGRID_URL`.

There are no DNA API keys or service accounts. A token always represents a
person, and that person must exist in the production tracking system.

## The link to ShotGrid

Validating the token proves who the caller is. It does **not** prove they are
a DNA user. That check happens on the first data request:
`GET /projects/user/{user_email}` looks up a `HumanUser` whose `email` equals
the caller's email and returns `404` when there is none. The web app treats
that as "not allowed in".

Writes go to ShotGrid through a single **script user**
(`SHOTGRID_SCRIPT_NAME` / `SHOTGRID_API_KEY`). When DNA publishes a note it
resolves the draft owner's login from `author_email` and impersonates them
with `sudo_as_login`, so the Note shows that human as author — including when
the authenticated caller publishes someone else's draft. Two consequences:

- The draft owner's email must match a ShotGrid user's email **exactly**,
  or publishing on their behalf fails.
- What a caller can see and change is bounded by the script user's
  permissions, not the person's. Scope that script user accordingly
  (`backend/docs/SHOTGRID_SETUP.md`).

ShotGrid **auth** (`ShotgridAuthProvider`) and ShotGrid **prodtrack**
(`ShotgridProvider`) are separate. Auth only obtains and validates user
tokens; prodtrack still uses the script key for data.

## Who is the caller?

Every protected route validates the bearer token and requires `X-User-Id` to
match that principal (except `AUTH_PROVIDER=none` when the header is omitted).

Many endpoints also take a `user_email` in the path or body. That value is
**not** always the caller:

| Endpoints | `user_email` is... | Path/body mismatch |
|---|---|---|
| `/users/{user_email}/settings`, `/users/{user_email}/qc-checks`, `/users/{user_email}/qc-checks/{check_id}` | The caller (`SelfUserDep`) | `403 Forbidden` |
| Draft notes, `publish-notes`, `generate-note`, `run-qc-checks`, `/users/{user_email}`, `/projects/user/{user_email}` | **Data**: the owner of the draft or the person to look up | Not checked against the caller |

:::warning Any authenticated user can act for any draft owner
A dailies review is collaborative, so the web app reads everyone's drafts in
a playlist and can publish them all at once. The backend still requires the
caller's `X-User-Id` to match their own token; it does not require
`body.user_email` to match the caller on playlist-scoped routes. Your tool
should still pass the real reviewer's email on every draft so authorship in
ShotGrid is right, and must never hand its token to an untrusted client.
:::

## WebSockets

- **`/ws`** (outbound events) performs **no authentication**. Anyone who can
  reach the backend can subscribe to transcript and bot events. Keep the
  backend behind a network boundary.
- **`/transcription/extension/ingest`** (inbound transcripts) authenticates
  with query parameters, because browsers cannot set headers on a WebSocket:
  `token` is validated exactly like a bearer token, and `key` must equal
  `DNA_EXTENSION_KEY` when that variable is set. Identity headers are not
  available on this socket. Failures close the socket with code `1008` and a
  reason of `unauthorized` or `invalid extension key`.

See [Real-time](/api/realtime) for the frame formats.

## Error responses

| Status | When |
|---|---|
| `401` | Missing/invalid token, or bad login credentials |
| `403` | Valid token but missing/mismatched `X-User-Id`, or self-service path email mismatch |
| `503` | Upstream identity provider unreachable (ShotGrid / Google) |

```json
{ "detail": "Missing authentication credentials" }
```

Sent with `WWW-Authenticate: Bearer` on `401` credential failures.
