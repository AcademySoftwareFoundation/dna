# Authentication

Every request carries a DNA access token, except sign-in and the public
probes:

```http
Authorization: Bearer TOKEN
```

Public, no token needed: `POST /auth/login`, `GET /`, `GET /health`,
`GET /version-statuses`, `GET /api/mock-thumbnails/{version_id}`,
`GET /transcription/extension/health`. Every other reference page shows a
lock icon.

## Getting a token

Exchange a username and password for a token with `POST /auth/login`. The
body is form-encoded, as in the OAuth2 password flow:

```bash
curl -X POST "$DNA/auth/login" \
  -d username=jdoe -d password='...'
```

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_at": "2026-01-01T20:00:00Z",
  "user": { "sub": "jdoe", "email": "jdoe@studio.example", "name": "Jane Doe" }
}
```

Send `access_token` as the bearer token until `expires_at`. There is no
refresh endpoint: when a request returns `401`, sign in again.
`GET /auth/me` returns the `user` object for the token you send.

The deployment's `AUTH_PROVIDER` decides how the password is checked:

| `AUTH_PROVIDER` | Checks | Resulting identity |
|---|---|---|
| `shotgrid` | The ShotGrid login and password (`authenticate_human_user`) | `sub` is the ShotGrid login; `email` and `name` come from the `HumanUser` |
| `mock` (development) | Nothing; any password is accepted | `sub` and `name` are the username; `email` is the username if it contains `@`, otherwise `USERNAME@localhost` |

The ShotGrid auth provider can point at a different site from the production
tracking provider (`AUTH_SHOTGRID_URL`, `AUTH_SHOTGRID_SCRIPT_NAME`,
`AUTH_SHOTGRID_API_KEY`, each falling back to the `SHOTGRID_*` variable).
Sites that sign in through Autodesk Identity / SSO have no ShotGrid password
and cannot use `shotgrid` auth.

## What the token is

The token is a JWT that DNA signs itself with `JWT_SECRET_KEY` (HS256 by
default) and that lives for `JWT_EXPIRE_MINUTES` (default 720, 12 hours). Its
claims are the identity above (`sub`, `email`, `name`) plus `iat` and `exp`.
On every request the backend verifies the signature and expiry and reads the
caller from the claims; nothing about the session is stored server-side.

The claims are signed, not encrypted: anyone holding the token can read the
email in it. Treat the token like a password. Signing out in the web app
discards the token in the browser; a copied token keeps working until it
expires. Rotating `JWT_SECRET_KEY` invalidates every token at once.

There are no API keys or service accounts. A token always represents a
person. If you need unattended access, raise it with the deployment owner
rather than sharing a user's token.

## The link to ShotGrid

Production tracking calls run **as the caller**. For each request the
ShotGrid provider looks up the `HumanUser` whose `email` equals the token's
email (cached per process) and connects with that user's login through
`sudo_as_login`. Consequences:

- What a caller can see and change is bounded by **their own** ShotGrid
  permission group. The script user must be allowed to act on behalf of
  other users (`backend/docs/SHOTGRID_SETUP.md`).
- Notes published through DNA are authored by the user who published them,
  even when they publish other reviewers' drafts.
- The email from the auth provider must match a ShotGrid user's email
  **exactly** (case-insensitive). Otherwise every production tracking
  request returns `403` with `User not found in ShotGrid: ...`.

Auth and production tracking are configured separately. With
`AUTH_PROVIDER=mock` and `PRODTRACK_PROVIDER=shotgrid`, signing in as a
ShotGrid user's email acts as that user without a password, which is useful
in development and must never be deployed.

## Who is the caller?

Many endpoints take a `user_email` in the path or body. Only some of them
check it against the token:

| Endpoints | `user_email` is... | Mismatch |
|---|---|---|
| `/users/{user_email}/settings`, `/users/{user_email}/qc-checks`, `/users/{user_email}/qc-checks/{check_id}` | The caller | `403 Forbidden` |
| Draft notes, `publish-notes`, `generate-note`, `run-qc-checks`, `/users/{user_email}`, `/projects/user/{user_email}` | **Data**: the owner of the draft or the person to look up | Not checked |

:::warning Any authenticated user can act on any user's drafts
A dailies review is collaborative, so the web app reads everyone's drafts in
a playlist and can publish them all at once; the backend allows the same to
any valid token. Published notes are authored by the caller, not the draft
owner. Never hand a token to an untrusted client.
:::

## WebSockets

- **`/ws`** (outbound events) performs **no authentication**. Anyone who can
  reach the backend can subscribe to transcript and bot events. Keep the
  backend behind a network boundary.
- **`/transcription/extension/ingest`** (inbound transcripts) authenticates
  with query parameters, because browsers cannot set headers on a WebSocket:
  `token` is verified exactly like a bearer token, and `key` must equal
  `DNA_EXTENSION_KEY` when that variable is set. Failures close the socket
  with code `1008` and a reason of `unauthorized` or `invalid extension key`.

See [Real-time](/api/realtime) for the frame formats.

## The 401 response

```json
{ "detail": "Missing authentication credentials" }
```

Sent with `WWW-Authenticate: Bearer`. Other `detail` values you will see are
`Token has expired`, `Invalid token: ...` (bad signature or malformed token),
and, from `POST /auth/login`, the auth provider's reason such as
`Invalid username or password`.
